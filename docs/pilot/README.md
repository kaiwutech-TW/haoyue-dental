# 好約試用：先驗證牙醫流程，再考慮 LINE 與收費

狀態：測試工具與任務已備妥，正式站已完成工程驗收；尚無真人試用結果。自動測試、開發者操作與合成資料均不計為受訪者。

測試入口：[繁體中文](https://haoyue-dental.vercel.app/)／[English](https://haoyue-dental.vercel.app/en)。使用各自的無痕視窗。新會話有獨立合成預約；切換患者會建立新示範，重載則保留目前會話。不要輸入真實姓名、電話、病歷或診所機密。

## 怎麼開始

1. 先做營運唯讀檢查，再由主持人實際走一遍改期、確認、重載。見 `../DEPLOYMENT.md`。
2. 分別找 3 位牙醫櫃台／店家，以及 5 位未接觸本專案的人。這是探索性樣本目標，不是統計驗證門檻，也不必湊數後才記錄問題。
3. 先取得參與者同意。預設只記匿名筆記；錄音、錄影另行徵得同意。由 Kai 自行邀請，本工具不代寄訊息。
4. 對一般使用者只給 `user-tasks.md`，不要先教按鈕或透露正確流程。主持人用 `observer-guide.md` 記錄。
5. 店家先訪談目前工作，再測原型，使用 `clinic-guide.md`。不要先宣傳 AI 多厲害。
6. 結果填在 `results-template.md`；標註版本、語言、裝置、參與者類型、是否獲得提示、任務結果、卡點與原話。沒有測到就填「未測」。

## 先決定量什麼

- 是否在未提示下看懂產品用途？請對方用自己的話說。
- 從開始到正確儲存改期的時間；另外量首次理解用途的時間。
- 確認前，是否知道原預約仍保留？確認後能否指出新時間？
- 是否有誤取消、誤確認、重複點擊、把示範誤認成真實掛號？
- 店家是否能指出具體需求、頻率、目前處理方式與採用障礙？
- 比較同一任務的現行方法。不能把不同人、不同難度任務的時間差直接當產品效益。

成功、失敗、提示後成功與中止分開計算；報告分母與未完成原因，不只報最好的一次。不記「使用者很喜歡」這類沒有行為依據的結論。

## 決策關卡

- **修正後再測**：發生錯誤異動、誤認確認狀態、看不到失敗結果或真實掛號誤認，先修正再繼續擴大試用。
- **值得做 LINE 小試點的訊號**：多位櫃台獨立指出同一個高頻流程，而且店家願意提供負責人、安排試用時間、確認哪些資訊可使用與誰接手例外。只有「有興趣」不夠。
- **值得測收費的訊號**：與店家約定明確試用範圍、成功指標、維護責任及可接受的方案，並拿到實際付費試用或明確採購下一步。口頭願付價格仍是假設。
- **考慮其他產業的時點**：先記錄牙醫試點哪些部分確實可共用，再訪談美容／美髮、汽車保養等候選產業。依預約時長、人員資源、訂金、改取消規則等差異評估；不先宣稱一套能直接通用。

## 後續 LINE 試點的必要工作

這些尚未實作，也不屬於本輪 hackathon 完成宣稱：官方帳號與 webhook 驗證、身分綁定與店家授權、訊息重送去重、多店資料隔離、人工接手與服務時間、實際行事曆對接、穩定推論代管、用量歸屬與退出／資料刪除流程。先用合成資料驗證，再另行確認真實資料與營運範圍。
